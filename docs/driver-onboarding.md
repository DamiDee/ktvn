# Driver onboarding

The six-step application at `/driver/apply` registers a new driver through the existing public `POST /users` endpoint. It sends a `CreateUserDto` with `role: "Driver"` and a nested `driver_details: DriverRegistrationDto`. It does not create a separate car or call an admin-only user endpoint.

All document and photo fields contain **raw Base64 file contents**, without a `data:...;base64,` prefix. Files are retained only in the in-memory application draft until submission. Files are sent with the registration JSON; there is no separate upload request. Successful submission clears the draft. Passwords are kept only in the final form and are never stored in the application store or browser storage.

JPG and PNG originals can be up to 25 MiB. Large images are resized proportionally (up to a 2000-pixel longest edge, decreasing to 1024 if needed) and encoded as JPEG, applying camera orientation and flattening transparency onto white. Compression progressively reduces quality to meet a per-photo budget. Small images remain unchanged. The upload shows original and prepared sizes and offers a preview to check readability. PDFs are limited to 1 MiB each and are not recompressed; oversized PDFs are rejected with instructions to use a smaller PDF or a photo.

`NEXT_PUBLIC_MAX_APPLICATION_BYTES` controls the complete UTF-8 JSON body budget, including Base64 expansion and all account fields. The conservative app default is 2 MiB; **the API/proxy limit is still unconfirmed**. The photo target reserves 64 KiB for fields and divides the remaining budget across eight Base64 files (about 186 KiB per photo at the default). A lower configured budget also reduces the PDF cap. The builder and registration service both refuse oversized requests before sending. Several individually valid PDFs can still exceed the combined budget. Confirm the smallest limit across the API and hosting proxy, set the app budget below it, and rebuild/redeploy; this public setting is fixed at build time. The API must also enforce its own limits. A readable server 413 returns the user to the document step without clearing the draft; account creation is never automatically retried.

The payload maps licence classes to `B`, `C`, `D` or `E`, uses `YYYY-MM-DD` for licence expiry, and sends vehicle year and passenger seats as integers. Selecting both driving tracks sends `Both`; the individual selections send `Volunteer` or `Professional`. City and vehicle photo are required by the application. Worker applications clear guarantor fields; non-worker applications clear the department and include the guarantor details and photo.

Each step validates its fields, and submission revalidates the complete draft. API failures keep the draft available for correction and retry. Account creation is never automatically retried, and the UI prevents duplicate submissions. Success directs the applicant to sign in; registration itself does not authenticate the new account. Explicit demo mode keeps submission local.

The API user type includes nullable `driver_profile` and `car` fields. `src/types/driver-api.ts` defines the registration, profile and public driver-view DTOs. The supplied schemas are reflected in the repository and public OpenAPI copies. Public ride projections retain vehicle capacity and handle nullable profile values.

Run `node --experimental-strip-types --test tests/driver-registration.test.mjs` for payload, file encoding, validation, transport and response coverage. Transport tests mock requests and do not create real accounts.
