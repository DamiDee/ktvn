# Driver sign-in and account

Live driver sign-in opens `/rides/driver` immediately, using the role returned by `POST /auth/login`. Account retrieval does not delay navigation. The paid-rides shell then retrieves the signed-in user's canonical `UserDto` from `GET /users/{id}`, using the remembered user ID and HTTP-only authentication cookies. It retrieves the linked vehicle from `GET /cars/{car_id}`. Both bare DTOs and the API's `{ message, data }` envelope are supported.

The shared viewer query provides the driver's actual name and photo to the Drive tab. The Account tab displays personal details, masked NIN, verification status, driving tracks, licence information, worker/guarantor details, linked car specifications and submitted documents. Raw Base64 JPEG/PNG photos become image data URLs, and supported documents can be previewed. Account information remains in memory and is cleared at account boundaries; no profile documents or identity numbers are written to browser storage.

Pending drivers can view their dashboard, account and documents. Going online requires an approved/verified/active driver profile and a verified linked car; the API remains authoritative for every availability change. Account refresh and returning to the app refresh approval information. A failed car lookup leaves personal and driver details visible with a refresh action. Expired sessions and mismatched account records are rejected.

Paid rides now defaults to `api` whenever Free Buses uses live authentication, including production builds. Explicit Free Buses demo mode defaults to `mock`. `NEXT_PUBLIC_PAID_RIDES=off|mock|api` remains an explicit override. The REST base defaults to `NEXT_PUBLIC_FREEBUS_API_BASE_URL` (or the existing API default); the socket URL defaults to that base with `/rides/ws` and the corresponding `ws`/`wss` protocol. The existing paid-rides REST and socket environment variables override these defaults. Deployment values are compiled into the browser bundle and require a rebuild when changed.

The real API must allow the app's origin with credentialed CORS, issue cookies usable by the deployment, and accept authenticated WebSocket connections. These infrastructure properties require live validation on the deployed origin. Chat and SOS feature flags retain their existing explicit enablement rules. This integration does not deploy the application or establish that the live ride lifecycle has been verified.

Run `node --experimental-strip-types --test tests/paid-rides-profile.test.mjs` for routing, configuration, profile mapping, Base64 previews, verification gating, partial failures and account-isolation coverage. Tests use synthetic records and mocked requests.

Local validation passed: all 135 automated tests, lint, TypeScript and the Webpack production build. An isolated browser run against a synthetic API verified driver login → `/rides/driver`, the actual profile/photo/car display, pending approval blocking online availability, approval refresh, going online/offline, and logout returning to login. No real account or ride was changed. The deployed cookie, socket and ride-lifecycle checks above remain outstanding.
